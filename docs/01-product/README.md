# 产品说明

Cabbage 通过仓库本地 Markdown、验证状态和 CI 保留变更依据，不替代开发、评审或测试工具。

## 默认体验

新项目的普通功能、修复和重构只需要一份 `tasks.md`：

1. 实现前填写目标或问题、最小方案和风险。
2. 完成任务并记录实际验证命令与结果。
3. 验证 `implementation`，通过合并门禁，确认合并后归档。

不要求额外 PRD、技术方案、测试计划、DAG、多方案对比或重复 SOP。
产品目标和测试证据由该记录承载，不为满足 CI 再创建重复文档。
`change.yaml` 与 `state.json` 仍由 CLI 管理，一份记录不是只有一个磁盘文件。

## 风险边界

面向 agent 的分发形态是按任务场景拆分的七个 skill（见 `skills/`）：入口 `cabbage` 负责选路与组合编排，
`cabbage-change` 覆盖变更流程与门禁，`cabbage-research` 负责调研与选型，其余分别负责决策记录、
事故复盘、文档写作与存量接入。单个 skill 可独立安装，不依赖兄弟 skill。
调研本身不建变更记录，结论需要落地时再由 `cabbage-change` 创建变更。

| 影响 | 增加的文档 | 阶段 |
| --- | --- | --- |
| 架构 | ADR | `adr` |
| 外部 API | API 设计 | `api` |
| 数据库 | 数据库设计与迁移/回滚 | `database` |
| 安全 | 安全评审 | `security` |
| 高风险发布 | 部署与回滚方案 | `release` |

通过 `impact --set` 激活，相关方案须在实现前验证。实际执行结果记入 `tasks.md`。
高风险影响的当前文档目录规则仍生效；`operations / data / performance` 的既有目录规则也保留。
风险标记由人或 Agent 声明，工具不自动推断，也不证明方案正确。

## 兼容性

新默认只随新项目初始化提供。旧项目的配置、工作流、记录和签名不自动改写。
`architecture / migration / integration / hotfix / incident` 保留已有专项工作流。
历史 ADR 中的全流程和 DAG 决策是演进记录；新默认以本文为准，不静默改写历史。

## 校验与同步

- `pending`：未验证；`done`：指纹匹配；`stale`：验证后的输入变化；`skipped`：未启用。
- `validate` 允许草稿；`verify` 拒绝占位符、未完成清单及错误链接等，并记录指纹。
- `sync` 复制有映射的文件，不检查验证状态或自动合并当前事实；发布前先通过合并门禁。
- `archive` 检查阶段门禁后同步并保留变更历史，不检查 Git 是否已合并。
- `ci` 检查提交差异、门禁和适用目录；`docs build` 单独构建 VitePress 站点。

分支保护、人工审批和策略文件权限由代码托管平台提供。
