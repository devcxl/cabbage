## 亮点

### 1. 新项目的变更模型收敛为「一份记录 + 按风险展开」

- 新项目只保留 `change` 与 `incident` 两类工作流；普通变更默认只需要一份
  `tasks.md`，不再强制 PRD、技术方案、测试计划和 DAG（`7a4c3e5`、`eedf5f9`）。
- 高风险仍按需展开：`design`、`rfc`、`architecture`、`api`、`database`、
  `security`、`deployment` 各自生成专项文档并设置实现前门禁。
- `gate` 目标泛化为「任意阶段 id / merge / archive」，未知变更类型会列出可用类型。
- `incident` 工作流第三阶段统一命名为 `tasks`。

### 2. 任务 DAG 与派发视图

- `cabbage tasks` 支持任务依赖、并行分组、就绪/阻塞统计和 Mermaid 图（`3e86f42`、`f47be05`）。
- 普通清单不会被伪装成结构化 DAG；`tasks --export-dag` 已移除，派发职责交给编排侧（`7a4c3e5`、`ac2c192`）。

### 3. Skill 按场景拆分

- 单一长指南拆为 7 个 skill：`cabbage`（选路）以及 `cabbage-change`、
  `cabbage-research`、`cabbage-decision`、`cabbage-incident`、`cabbage-docs`、
  `cabbage-adopt`（`2b77d64`、`99442df`）。
- 每个 skill 带独立 references，可单独安装；测试校验 frontmatter、相对链接和同族清单完整性。

### 4. 闭环与诚实性

- `cabbage status` 标出全部阶段已验证、可归档的变更（`ready_to_archive`），文本输出附带归档提示（`9212d55`）。
- 生成的 CI 模板在缺少 `tests/` 时输出 `::warning::`，不再静默跳过测试（`9212d55`、`4a6f18c`）。
- `validate` / `status` 容忍缺失的 `.cabbage/changes/` 目录，修复了归档最后一条记录后 CI 失败的问题（`f966c7c`）。
- agent 契约补充代码评审与合并后归档边界。

### 5. 文档站点升级 VitePress

- VuePress 迁移到 VitePress 1.6.4，支持 Mermaid，侧边栏由实际存在的页面动态生成（`ec3c037`、`9b25574`、`11db1fb`）。
- 文档目录 `04-data` 更名为 `04-domain`，并重写目录用途、sync 目标与门禁规则说明（见破坏性变更）。

### 6. 发布与分发

- 版本号单源到 `cabbage_cli/__init__.py`，`pyproject.toml` 动态读取（`5c78258`）。
- 补齐 `LICENSE`；保留 `scripts/install.sh`、AUR PKGBUILD、Debian 包构建和 GitHub 草稿 Release 流程。
- `status` / `next` / `impact` 默认输出改为可读文本，`--json` 保持机器可读输出（`0e4816d`）。

## 破坏性变更

| # | 变更 | 影响对象 | 迁移方式 |
| --- | --- | --- | --- |
| 1 | `docs/04-data/` → `docs/04-domain/`（`848f3b9`） | 既有项目 | 重命名目录；更新 `.cabbage/config.yaml` 中 `ci.current_state_rules.database` 与可选的 `docs.mapping`；从 `impact_fields` 移除 `data`；重跑 `validate` / `ci` |
| 2 | 新项目工作流 8 类收敛为 `change` + `incident`（`7a4c3e5`） | 新初始化项目、脚本 | `new feature/bugfix/refactor` 改用 `new change`；`architecture` 加 `--set architecture=true`；`migration` 加 `--set database=true`；`integration` 加 `--set api=true`；`hotfix` 用普通 `change` |
| 3 | 移除 `cabbage tasks --export-dag`（`7a4c3e5`） | 依赖导出 DAG 的脚本 | 改用 `cabbage tasks --json` 读取就绪/阻塞视图；派发由 Agent/插件编排侧负责 |
| 4 | 移除 `data` 影响字段（`ee1d7fa`） | 使用 `impact --set data=true` 的脚本 | 改用 `database=true`；历史记录保留 `data` 键不会导致校验失败 |
| 5 | 版本号来源改为 `cabbage_cli.__version__`（`5c78258`） | 解析 `pyproject.toml` 静态 `version` 的工具 | 改为读取包属性 `cabbage_cli.__version__` 或 `cabbage --version` |
| 6 | 文档站点 VuePress → VitePress（`ec3c037`） | 引用 `.vuepress` 路径或旧构建脚本的项目 | 改用 `.vitepress`；构建环境 Node.js 22 + pnpm 10 |

第 1 项已明确不提供兼容分支。仓库记录中已知受影响的下游项目：
`LaseAI`、`fcitx5-voice-input`、`trading-web3-ai`，需要人工迁移配置与目录。

第 2 项只影响**新初始化项目**。既有项目 `.cabbage/workflows/` 原样保留，
`cabbage new feature` 等旧类型仍按项目自身工作流解析；不要用 `init --force` 升级，
它会覆盖项目配置与工作流。

## 发布步骤

以下步骤供维护者在合并后执行；本 PR 不执行标签、推送标签和发布。

### 1. 确认版本已同步

```bash
# 版本已由本 PR 同步为 0.2.0；确认工作区干净后再继续
git status --short
python scripts/sync-vendor.py   # 应为无变化
```

### 2. 本地预检

```bash
python -m unittest discover -s tests -v
python -m compileall -q cabbage_cli tests
python -m cabbage_cli validate --all
python -m cabbage_cli ci --base origin/master
python -m build
./scripts/build-deb.sh v0.2.0
```

### 3. 隔离安装验证

```bash
python3 -m venv /tmp/cabbage-release-venv
/tmp/cabbage-release-venv/bin/pip install dist/project_docs_cabbage-0.2.0-py3-none-any.whl
/tmp/cabbage-release-venv/bin/cabbage --version
mkdir /tmp/cabbage-smoke && cd /tmp/cabbage-smoke && git init -q .
/tmp/cabbage-release-venv/bin/cabbage init --no-vendor-cli
```

### 4. 打标签并推送

```bash
git status --short          # 应为空
git tag -l 'v0.2.0'         # 应无输出
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
```

### 5. 审核并发布草稿 Release

- `.github/workflows/release-draft.yml` 会运行测试、校验标签版本、构建 wheel/sdist 和 `.deb`，
  创建 **draft** Release。
- 用本文件的「亮点 / 破坏性变更 / 已知限制」替换 `--generate-notes` 的自动内容。
- 核对资产版本号与标签一致后再手动发布。

### 6. 发布后验证

- 从 Release 下载 wheel 和 `.deb`，在干净环境安装并执行 `cabbage --version`。
- 访问 GitHub Pages 文档站点，确认 `04-domain` 页面和 Mermaid 正常。
- 注意：`scripts/install.sh` 克隆的是**默认分支**而不是标签，发布后安装到的内容是
  `master` 当前 HEAD；若发布后还有新提交，两者可能不一致。

## 已知限制

1. **历史草稿 Release 制品版本错误。** `v0.1.0` 和 `v0.1.1` 的草稿 Release 中，
   Python 制品仍是 `0.1.0`（`v0.1.1` 标签指向的代码版本是 `0.1.0`）。
   当前工作流已加入标签/版本一致性校验，不会重演；这两个草稿不要发布，建议确认后删除。
2. **未发布到公共 PyPI。** 分发依赖安装脚本、AUR、`.deb` 和 GitHub Release。
3. **没有 CHANGELOG。** 仓库只有 `docs/12-release/README.md` 的发布流程说明和单次发布记录；
   每个版本的说明需像本文件一样单独维护，GitHub 草稿 Release 默认使用 `--generate-notes` 的提交摘要。
4. **安装脚本不锁定版本。** `install.sh` 克隆默认分支，无法安装指定 tag。
5. **无静态类型检查。** 只有 `compileall`，没有 mypy/pyright/ruff 门禁。
6. **Python 版本覆盖有限。** 本地只在 3.14.7 验证，CI 使用 3.12；声明的下限 3.10/3.11 未在本机实测。
7. **文档构建有体积警告。** VitePress 报告部分 chunk 超过 500 kB（Mermaid 相关），不影响构建，但会影响首屏加载。
8. **根目录快照文档过期。** `RUNTIME.md` 正文仍写 `__version__ = "0.1.0"`、8 个工作流和
   `feature.yaml`，顶部已加历史快照声明；`AUDIT.md` 也是 2026-09 的快照。
   二者应视为历史材料，不要作为当前行为依据。
9. **存量项目不会自动迁移。** 旧工作流、`04-data` 配置和验证状态都保持原样；
   升级 CLI 后需用 `cabbage status` / `cabbage next` 查看实际阶段。
10. **本仓库 `ci --base origin/master` 在 master 上是空差异。** 本地通过只能证明命令可用，
    PR 门禁由远端 CI 在拉取请求上执行；历史 master CI 已在 HEAD 通过。
