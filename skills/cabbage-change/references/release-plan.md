# 发布与回滚方案

`deployment=true` 时激活 `release` 阶段，填写 `release-plan.md`（必需标题
`Deployment`、`Rollback`、`Verification`）。本文件说明怎么写。

**核心原则：这是实现前写的计划，写"将要做什么"和"什么信号说明失败"，不写尚未发生的成功结果。**
真实执行记录写入变更记录的 `Verification`。

## 何时声明 deployment

| 情况 | 是否需要 |
| --- | --- |
| 需要停机、分批发布、灰度或特殊顺序 | 是 |
| 需要回滚方案，或回滚涉及数据处置 | 是 |
| 有兼容性窗口、双写、双读或迁移切换 | 是 |
| 日常合并后由流水线自动发布，无特殊顺序 | 否 |
| 只改文档、注释或测试 | 否 |

不要为了"更稳妥"给每次合并都加 `deployment=true`，那会导致专项文档被形式化填写。

## Preconditions：可勾选的前置条件

每条都要能被客观判定，不要写"确认无误"这类无法验证的表述：

- 数据库备份已完成且验证可恢复
- 下游消费者已升级到兼容版本（列出服务与版本）
- 回滚所需的上一个镜像/制品已确认可用
- 容量或配额已满足新版本的峰值

## Deployment：顺序化的步骤

用表格按顺序写，每步给出**成功信号**，没有信号就无法判断该继续还是回滚：

| Order | Action | Owner | Success signal |
| --- | --- | --- | --- |
| 1 | 发布兼容版本（双读） | @alice | 新版本实例健康检查通过，错误率持平 |
| 2 | 执行 schema 迁移 | @bob | 迁移任务退出码 0，`schema_migrations` 出现该版本 |
| 3 | 切换流量至新版本 | @alice | 5xx 比例 < 0.1%，P99 延迟未上升 |

要点：

- 顺序必须体现依赖：先部署后迁移，还是先迁移后部署，写清楚。
- 明确谁负责每一步，避免出现无人负责的步骤。
- 灰度发布要写清分批比例与观察时长，以及每批的放行/终止判据。

## Rollback：先定触发条件，再写步骤

**触发条件必须是可测量的**，否则回滚会变成临场争论：

| 可测量触发条件 | 说明 |
| --- | --- |
| 5xx 比例持续 5 分钟 > 1% | 明确阈值与持续时间 |
| P99 延迟超过基线 2 倍 | 需给出基线值 |
| 数据校验发现不一致记录 > 0 | 数据类变更必填 |
| 关键业务流程失败率上升 | 指明具体指标 |

步骤要说明**顺序、责任人和数据处置**——这是最容易缺失的部分：

- 回滚顺序是否与部署顺序相反？是否需要先停写再回滚？
- 已写入的新格式数据如何处理：保留、转换还是清除？
- 不可逆操作（如已执行的破坏性迁移）如何应对，是否有预案？

如果某步**无法回滚**，必须显式写出来并说明补偿措施，不能留空。

## Verification：上线后确认

每条给出检查方法、期望结果与执行人，例如：

| Check | Method | Expected result | Owner |
| --- | --- | --- | --- |
| 核心链路可用 | 冒烟脚本 `make smoke` | 全部通过 | @alice |
| 错误率恢复基线 | 监控面板 `api/overview` | 5xx < 0.1% 持续 30 分钟 | @bob |
| 数据一致性 | 校验脚本 `make verify-data` | 差异记录数为 0 | @bob |

## Monitoring 与 Communication

- 观察窗口：明确观察多久才算发布完成，避免过早宣布成功。
- 升级路径：观察期内谁在值守、什么情况下升级处理。
- 对外沟通：受影响方、状态页更新、是否需要发布说明。

## 与其他文档的边界

| 内容 | 归属 |
| --- | --- |
| 表结构、迁移与数据回滚 | 数据库设计文档（`database` 阶段） |
| 接口兼容性与弃用窗口 | API 设计文档（`api` 阶段） |
| 架构层面的取舍 | ADR（`adr` 阶段） |
| 本次发布的具体顺序、回滚与验证 | 本文件 |

## 常见错误

- 把回滚写成"回退到上一版本"，没有顺序、责任人和数据处置。
- 触发条件写成"出现异常时回滚"——无法在压力下判定。
- 只有部署步骤，没有验证步骤，无法确认发布是否成功。
- 实现前就填写"验证结果：通过"，等于伪造证据。
